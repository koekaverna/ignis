## Flatness — the claim that matters

V-30 restated the criterion as "no monotonic trend past 5M". Least-squares slope of `rss_kb`
against cumulative requests, over the hello phase with the fiber pool settled at 64:

| series | n | band | slope | first/second-half drift | extrapolated to 100M req |
|---|---|---|---|---|---|
| run A, samples 1–7 (0.15M–1.07M) | 7 | 176 kB (0.40%) | **−45.6 kB / 1M req** | +5 kB (+0.011%) | −4.5 MB |
| run B, samples 2–39 (0.24M–5.12M) | 38 | 268 kB (0.61%) | **+8.4 kB / 1M req** | −5 kB (−0.012%) | **+0.8 MB** |
| run B, last 10 (3.84M–5.12M) | 10 | 176 kB (0.40%) | +36.8 kB / 1M req | +26 kB (+0.058%) | +3.6 MB |

**Flatness holds.** Over 4.87M requests the slope is +8.4 kB/1M — 0.019% of RSS per million
requests, well inside sample noise — and the sign flips between runs and between windows, which is
what noise does and a leak does not. The PHP heap is flat **to the byte** over all 39 samples, as
V-10 found over 3. The E3 target "±2% over 1M requests" is met with an order of magnitude to
spare. The only step change remains the fiber pool growing to peak concurrency (64 → 500) during
the sleep workload, after which nothing grows. Threads stayed at 1, `stalled: 0`, `restarts: 0`,
no thread deaths across 8.5M requests (V-30's defect stays fixed).

## Delta against V-10 — and why "extensions" only explains a sixth of it

| | V-10 (2026-09-16) | now (2026-09-18) | delta |
|---|---|---|---|
| RSS, hello phase, 1 thread, 64 fibers | **26.2 MB** | **42.7–42.8 MB** | **+16.5 MB (+63%)** |
| PHP heap, same phase | 1,652,432 B | 1,710,880 B | +58,448 B (+3.5%) |
| `mem_real` | 2,097,152 B | 4,194,304 B | one 2 MiB allocator-chunk step, not a 2 MB regression |

The brief framed this delta as the cost of building extensions in. **The measurement does not
support that framing**, and the decomposition says why. Resident set by mapping, same build, 1
thread, after 3,000 requests (RSS 41.4 MB — load-insensitive, taken while the box was busy):

| mapping | resident |
|---|---|
| `/opt/php85-zts/lib/libphp.so` | **8,956 kB** |
| `[anon:mimalloc]` | 8,088 kB |
| `libcrypto.so.3` | 3,820 kB |
| `[heap]` | 3,332 kB |
| `target/release/ignis` | 3,016 kB |
| `/dev/zero` | 2,756 kB |
| `libc.so.6` | 2,000 kB |
| `libcurl` 960 / `libgnutls` 904 / `libxml2` 732 / `libm` 664 / `[anon:zend_alloc]` 652 | 3,912 kB |
| whole process (`smaps_rollup`) | Rss 41,660 kB, Pss 32,845 kB |

`libphp.so` grew 50.3 → 67.5 MB **on disk**, but it is demand-paged and only **8.96 MB is
resident** — 17.2 MB of added disk cannot become 16.5 MB of added RSS. Three independent facts
bound the extension share:

1. Resident `libphp.so` is 8.96 MB total, core PHP included.
2. The owner's own 2026-09-17 before/after put the extension cost at **+3.0 MB** (34.6–35.0 →
   37.6–37.8 MB on a trivial script).
3. That measurement's **pre-extension** baseline was already **34.6 MB — 7.7 MB above V-10's
   26.9 MB**, so most of the growth predates the extensions.
4. `mimalloc` (8.1 MB resident) landed 2026-09-15, *before* V-10 — it is not new.

So the +16.5 MB is approximately: **~8 MB from runtime changes between 2026-09-16 and 2026-09-17,
~3 MB extensions, ~5 MB from runtime changes since** — 281 commits separate V-10 from HEAD.
Attributing it to the extension build would be wrong. Whether the ~13 MB of runtime growth is
intended is a separate question this item did not ask and this measurement cannot answer; it would
need a bisect over those 281 commits.

## What the instrument reports today

`/stats` (`examples/hello_server.php:85`) already separates the two quantities — no change needed
for a 1-thread run:

- `mem` = `memory_get_usage()` — PHP heap in use, **this thread only** (the Zend MM heap is
  thread-local under ZTS).
- `mem_real` = `memory_get_usage(true)` — the allocator's OS-facing arena, moves in **2 MiB
  chunks**, far too coarse to show a slow leak.
- `rss_kb` = `VmRSS` from `/proc/self/status` — **whole process**: every thread's heap plus
  `libphp.so`, the tokio side, Rust allocations and thread stacks.

One limit to record before E3 is re-run at more than one thread: `/stats` is served by whichever
worker the dispatcher picks, so at `--threads N` `mem` is one thread's heap, not the PHP side's.
At `--threads 1` — how V-10 and both runs here were done — it is the whole PHP side, which is why
the "flat to the byte" claim is clean. At N>1 it needs either a per-thread sum or the number
stated as "one thread's heap".
