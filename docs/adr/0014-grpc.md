# ADR-0014 — gRPC on the shared hyper/h2 stack with an opaque-bytes codec

Status: accepted (Cycle 14, 2026-09-16; V-20). Affects pain-map items: RoadRunner 4 ("one call per worker at a time" / no in-process streaming), Swoole 3 (no gRPC without a sidecar). Depends on ADR-0007 (parking), ADR-0009 (cancel-on-drop), ADR-0010 (least-inflight dispatch), ADR-0013 (`Op::Custom` seam).

## Decision

1. **Server**: gRPC requests are detected on the existing hyper listener (`content-type: application/grpc*`) and framed by `tonic::server::Grpc` with a `RawCodec` (`Encode = Decode = Bytes`). One Rust path (`server_streaming`) serves both unary and server-streaming handlers; the PHP handler receives an `Ignis\Http\Request` whose body is the request message and answers through `ignis_grpc_send(id, bytes)` / `ignis_grpc_end(id, code, message)`. Dropping the response stream cancels the request fiber (same `cancel_request` as HTTP).
2. **Client**: `ignis_grpc_call(url, path, bytes, streaming)` and `ignis_grpc_recv(handle)` are `Op::Custom` futures over a per-URL `tonic::transport::Channel` created with `connect_lazy()`. Unary resolves to the reply bytes; server-streaming resolves to a handle and each `recv` is one op (one fiber suspension per message).
3. **Protobuf stays in PHP**. No `.proto` is compiled into the Rust build; the demo ships a minimal wire encoder (`Ignis\Grpc\Proto`) and real applications use `google/protobuf`.
4. **Not in scope**: client-streaming and bidi (they need a request-side stream into PHP: an `Op::GrpcRecvRequest` per message, same shape as the client `recv`), TLS on the listener, reflection, compression, deadlines beyond tonic's `grpc-timeout` handling, per-call metadata on the client.

## Consequences

- One listener, one h2 implementation, one dispatch policy for HTTP and gRPC. A gRPC request costs the same reactor round trip as an HTTP request plus tonic's framing.
- The response body type of the hyper service changes from `Full<Bytes>` to `tonic::body::Body` (a boxed body with `Status` errors); plain HTTP responses are wrapped, nothing else about them changes.
- Adding `tonic` (server + channel features only) is +~40 crates over the current tree; `tonic-build`/`prost` are not needed.

## Kill criterion

CLAUDE.md requires one on every ADR and this one had none until 2026-09-18.

Reverse this — go back to a generated codec, or to ext-grpc as the server — if either holds:

1. **The opaque-bytes codec stops being enough.** A feature a user needs (client streaming, bidi,
   compression, per-call deadlines propagated into `Ignis\deadline()`) turns out to require tonic's
   generated types rather than `Bytes` in and `Bytes` out. The measurement is the diff: if carrying it
   in userland PHP costs more code than generating the types would, the codec choice has expired.
2. **The PHP-side codec dominates.** V-20 put Ignis at 16.7k req/s against a pure-tonic ceiling of
   21.1k on the same box — 79 % of a Rust server doing the same work. If a profile of a realistic
   message (not a hello) shows PHP's own encode/decode above half the request, the argument that the
   codec belongs in PHP rather than in Rust is gone.

What would *not* reverse it: RoadRunner or ext-grpc getting faster. The comparison in V-20 is about
where the work happens, and the build complexity it names (77 minutes of C-core, 47.6 MiB of
`grpc.so`, three linker workarounds) is a standing cost this decision avoids whatever the numbers do.
